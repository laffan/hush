# Hush — Technical Overview

This document is for people and coding agents working on the codebase. It covers architecture, conventions, cross-module contracts, and lessons learned — not feature behaviour (see [README.md](README.md)) and not line-by-line implementation, which the code itself documents heavily in comments. Deep dives: [README-NOTEBOOK.md](README-NOTEBOOK.md) (canvas notebooks), [README-DRAWING.md](README-DRAWING.md) (stroke engine), [README-SYNC.md](README-SYNC.md) (desk storage + folder sync — **read before touching `desk_*.rs` or `sync/`**).

## Architecture

Hush is a [Tauri v2](https://v2.tauri.app/) app (macOS + iOS/iPadOS) with a vanilla JavaScript frontend and Rust backend. The editor is [CodeMirror 6](https://codemirror.net/) — no framework anywhere. Communication: `invoke` IPC for commands, `emit`/`listen` for events. Two webview entry points, built as separate Vite inputs: `index.html` → `src/main.js` (the editor window) and `settings.html` → `src/settings/settings-window.js` (a separate WebviewWindow with its own CSS pipeline).

## Development rules

- **No code file may exceed 700 lines.** Enforced by `scripts/check-line-limits.sh` (runs in `npm run build`). Split modules rather than growing them; the allowlist in `.line-limit-exceptions` requires a one-line justification per entry (currently `notebook/state.ts` and `notebook/drawing/engine/stroke.js`).
- **No framework dependencies.** Vanilla JS/TS, hand-rolled DOM.
- **Every JS-visible setting must have a field on the Rust `AppSettings` struct** (and every optional tree-node field on `TreeNode`). Serde silently drops unknown fields on the save/load round trip, so an undeclared setting resets to default every launch. Opaque/evolving shapes are stored as `serde_json::Value` (e.g. `persisted_panes`, `sticky_notes`, `desks_meta`) so Rust never has to learn their internals.
- **Heavy Rust work must be `async` + `spawn_blocking`.** A synchronous Tauri command runs on the webview's main thread and freezes the UI (harper's multi-second dictionary build, multi-MB `.hushnote` deflates). Similarly, multi-MB payloads cross IPC as raw byte bodies (`save_file_raw`), never JSON args — `JSON.stringify` of the payload on the JS thread stalls frames.
- **Rust→JS spans are converted to UTF-16 code units backend-side** (`char_to_utf16_range`) so CodeMirror positions apply directly.

### Conventions

- **Events** on `AppState` (`on`/`off`/`emit`, synchronous): the key ones are `settings-changed`, `theme-changed`, `style-changed`, `files-changed`, `file-opened`, `notebook-open`/`-unmount`, `pdf-open`/`-unmount`, `stack-open`/`-unmount`, `no-file-state`, `active-desk-changed`, `desks-changed`, `mode-changed`, `panes-changed`, `doc-content-changed`, `stickies-changed`, `you-are-here-changed`, `remote-settings-merged`. If a feature keys visibility off "what is open", it must handle **`no-file-state`** too (emitted by `clearActiveFile` — empty desk, deleted open file, archived desk), not just the open/unmount events.
- **`state.runtime`** holds cross-module side-channel data that is neither persisted settings nor evented state (`columnResizeHandler`, `visiblePaneCount`/`visiblePaneCentroid`, `docked*` footprints, `syncPulling`, `localSyncWriteFlag`, …). Never stamp ad-hoc `state._foo` fields.
- **Context ids**: every editing surface is addressed as `doc:`/`nb:`/`pdf:`/`st:` + fileId (panes' `ownerContext`, sticky targets, mode contexts); Desktops use `dt:` + containerId.
- **`window.__hush*` bridges**: the lazily-loaded notebook bundle never imports app modules. Cross-boundary hooks (`__hushOpenWikilink`, `__hushOpenPdfBookmark`, `__hushFileStickies`, `__hushCmdHeld`, …) are registered once from `main.js`/owning modules.
- **Transaction annotations**: programmatic doc rewrites (file loads, sync pulls, pane mirrors) carry `programmaticChange` so filters (ratchet, frontmatter protection) and dirty tracking can distinguish them from typing. `bypassRatchet` marks the one user edit a ratcheted selection may perform (strikethrough).
- **Command palette entries** are plain descriptors (`{ id, label, icon, ctx, action, hiddenIf?, keepOpen?, keywords? }`). The filter matches `label` plus the optional `keywords` string — the hidden half of a command's name, where a renamed command keeps its old wording searchable so muscle memory still lands. **`ctx: "doc"` means "the main editor isn't a notebook", which is not the same as "there is a document to act on"** — a doc open in a pane over a canvas is still a doc. A feature that rides `createBaseExtensions` (so it reaches panes and stack columns) gates on `hasActiveDocSurface` instead; spellcheck did not, so with a notebook open its command vanished *and* its toggle became a silent no-op. Running a command also hands focus back to the surface it ran against (the focused pane, else the main editor), and only when nothing else claimed it — a command that raises a modal keeps the caret. Focus is not cosmetic here: spellcheck only checks and underlines the surface that holds it.
- **The OS gets first refusal on a shortcut, and there is no working around it.** Strikethrough was ⌘\` for two releases and never fired: ⌘\` is "Move focus to next window" on macOS and cycles app windows on iPadOS, so on both platforms Hush ships on the keystroke was claimed before the web layer existed. No handler, at any layer available to us, can see a key the system took. Two rounds of increasingly clever matching went into that before the binding simply moved to **⌘-** (pairing with ⌘= for Highlight); `state-migrations.js` carries installs still holding the old default across. When a binding "does nothing", rule the platform out before writing another matcher.
- **Even so, a punctuation binding needs a physical-key route, and it must not trust any single signal.** CodeMirror matches on `event.key`, which a punctuation key can fail to deliver — grave arrives as `"Dead"` where it is a combining accent. Swapping in `event.code` is not the fix either: WebKit does not always populate `code`. `shortcuts.js#isPhysicalKey` walks `code` → `keyCode` → the character and takes whichever the platform filled in; `createStrikethroughFallback` (base-extensions.js) pairs it with `modifiersMatch` and deliberately does *not* re-check `event.key`, which is the comparison that fails. It is scoped to `PUNCTUATION_KEYS`: a letter binding always matches through the keymap, and a physical-key route for one would be wrong anyway — ⌘B is B's *character*, wherever the layout puts it. The settings recorder stores what a key produced (`shortcutKeyFromEvent`) rather than `event.key`, or recording a dead key saves `"Cmd+Dead"` — a binding nothing can match again.
- **A window-level keydown listener must skip `e.defaultPrevented`.** CodeMirror cancels the event for any binding it handled, and that is the signal the keystroke is spent. The PDF viewer's zoom listener is window-level so it works while the viewer is mounted anywhere — which means ⌘= / ⌘- reached it *and* Highlight / Strikethrough in a doc sharing the screen with a PDF pane. `window-shortcuts.js` has always had the guard; anything else listening at that level needs it too.
- **Every doc surface has to carry what the shared extension list carries.** `editor.js` builds its own list rather than using `createBaseExtensions`, so a feature added only to the shared one reaches panes, stack columns and the overlays but *not* the main editor — which is exactly where the user types, so it reads as the feature being broken rather than missing. The Cmd+\` fallback had this hole; so did **image paste**, which is why pasting a screenshot worked in a pane and did nothing in a Doc. Both are now in both lists. Check this first when something works "everywhere except the editor".
- **Shortcuts** (`src/shortcuts.js`): stored bindings distinguish `Mod`/`CmdOrCtrl` (either primary modifier) from strict `Cmd` and `Ctrl` tokens — that's how `Cmd+N` (new doc) and `Ctrl+N` (new notebook) coexist. `⌘P` and `⌘,` are hardcoded. Shortcut definitions/categories live in `settings/settings-tabs-shortcuts.js` (single source for the Settings tab and the Show Shortcuts modal); notebook tools have their own `shortcutNb*` fields read at canvas mount.
- **CSS**: per-module files under `src/styles/`; design tokens + the documented z-index scale live in `base.css` (`--z-pane: 90`, `--z-shelf: 150`, `--z-sidebar: 200`, `--z-sticky: 250`, `--z-overlay: 300`, `--z-popover: 400`, `--z-modal: 500/510`, `--z-modal-top: 9999`, drag ghost `2147483647`). Anything modal or higher must use a token. iPad-only reserved bands ride `--ipad-safe-top/bottom` (30 px under `html.ios:not(.phone)`) because `env(safe-area-inset-*)` doesn't report them. The settings window duplicates the tokens it needs (separate webview, no `base.css`).
- **Platform detection**: `isIOS`-style helpers accept UA `iPad|iPhone|iPod` OR (`platform` matches `Mac` AND `maxTouchPoints > 0`) — iPadOS 13+ reports as Macintosh, and some WKWebViews expose only 1 touch point; real Macs report 0. `isPhone()` additionally requires a narrow viewport; `html.ios` / `html.phone` classes gate CSS.

## Core state

`state/state.js` is a thin coordinator: settings (mirroring `AppSettings`, defaults in `state-defaults.js`), the file list + tree, mode flags, the editor handle, and the event emitter. Behaviour lives in siblings (`state-modes.js`, `state-snapshots.js`, `state-naming.js`, `state-convert.js`, `state-split-combine.js`, `state-tree.js`, `state-desks*.js`, `mode-context.js`, …) that take `state` as their first argument; `AppState` methods are one-line delegations where external callers need them.

**File tree.** `AppState.fileTree` is a nested tree of typed nodes `{ id, type, name, fileId?, children[], …decorations }`. Top level is always `type: "desk"` nodes; each desk owns namespaced specials `__inbox__:<deskId>`, `__images__:…`, `__pdfs__:…`, `__archive__:…`, `__trash__:…` (canonical list: `SPECIAL_KINDS` in `state-desks.js`), pinned in tail order Images | PDFs | Archive | Trash by `pinSpecialsInList` / `enforceSpecialPositions`. Same-type siblings can't share a name (names map to on-disk paths) — every create/rename path routes through `uniqueChildName`. Projects normalize docs-first / supplementary-after via `normalizeProjectChildren`. Traversal helpers live in `state/tree-helpers.js`.

**Desks.** Structural, always-on (a legacy flat tree is wrapped by a boot migration). Per-desk state splits three ways: *portable* meta rides the desk folder itself (style choice, ratchet flag, last file, desk stickies — see README-SYNC.md), *per-device* state stays in settings (`activeDeskId`, recents, local-folder last file), and the desk list/registry is two-way reconciled with the tree at boot. Desks are archived (zip), never deleted; the last desk can't be removed.

**Naming rule.** A doc's filename follows its first line (`state-naming.js`), triggered on cursor-leaves-line-1, blur, autosave, and a 1.5 s typing-idle debounce. Because that debounce fires the full pipeline on every pause, **the rename path must stay cheap**: it patches the one cached `state.files` entry in place rather than re-fetching the library (never call `list_files` on a hot path), and the wikilink rewrite that follows a rename runs in Rust (`wikilinks.rs`, `spawn_blocking`) — substring-pretesting each file, and reading a notebook's `data.json` straight out of its zip so the images inside are never decoded. Auto-rename is suppressed for Google-linked docs (the GDoc title owns the name), explicitly-named tabbed docs, and Local Sync files (disk is the source of truth).

**Projects.** `openProject()` concatenates child docs with `---hush-separator---` markers into one buffer; `saveProjectContent()` splits and writes each part back. Only docs join the buffer (`state.projectDocIds`); notebooks/stacks/PDF aliases ride along as supplementary sidebar children.

## Editor

`editor/editor.js` builds the main CodeMirror instance; **`createBaseExtensions(state, onChange, opts)`** builds the shared extension set (theme, markdown + custom inline parsers for `%%comments%%` / `==highlights==` / GFM tables / strikethrough, shortcuts, and nearly every plugin) used identically by floating panes, stack columns, and the Zen/Selection-Focus overlays — a feature added only to `editor.js`'s own list (e.g. proofread, spellcheck) is deliberately main-editor-only. Compartments expose theme / highlight / shortcut / editable reconfiguration.

**Per-editor mode contexts** (`state/mode-context.js`): focus, typewriter, and D.R.Y. are scoped per surface via a prototype-inheriting proxy over `AppState` (`Object.create(appState)` with own-property flags). **A fresh context seeds from the global flags**, not from off: these modes are per-surface once a surface exists, but "Typewriter mode is on" describes how the user is writing, not one editor. A pane opened *after* the toggle used to be silently exempt — and the global boundary line hides itself whenever a pane is active, so the mode read as simply not working in panes. Every entry point goes through `toggleModeOnContext`, which resolves the active context (`getActiveModeContext`) and falls back to the global toggles for the main editor, which does *not* use a context — the keyboard shortcut and the command-palette entry share it so a mode can't land on the editor behind the pane being typed in. Typewriter in a pane / stack column measures the **host box**, not the window (`pane-editor.js`): the boundary fraction is still the shared `state.typewriterPosition`, so the surfaces agree on where the line goes, and a `ResizeObserver` on the container re-pads and re-centres on every way a pane can be scaled (handles, dock reflow, size popover, window resize) — one observer instead of a hook per caller. Its runway is `padding-bottom` on `.cm-content` (see **Editor geometry**), never appended blank lines: a pane holds the whole file and writes the whole file back.

**Overlay editors** (Zen Focus, Selection Focus, Shuffle Editor) use a **shadow editor model**: a fresh `EditorView` (or plain-DOM node model, for Shuffle) seeded from the source, written back as a single replacement transaction on exit so undo collapses to one step. Each mounts outside `#editor-container`, so **anything carried by a container class rather than by an extension has to be bound to the overlay by hand** — `applyBlockCursor` for the cursor mode, `bindLineIndicatorToContainer` for the line indicator. The indicator's plugin rode in with `createBaseExtensions` and drew its overlay all along; with no `line-ind-*` class above it, every variant skinned to nothing and Zen looked like it had no indicator at all. Both overlays also reserve `--overlay-gutter` outside the text column for the indicator's margin marks and widen the stage by the same amount, so the measure stays the one the user dialled in. Reparenting the live editor DOM was tried and abandoned — stale geometry, focus fights. Selection Focus passes `{ fragment: true }` so ratchet treats the buffer as a slice (no title-line exception, no append-at-end).

**Ratchet** (`editor/ratchet.js`) owns both forward-only modes with a per-surface anchor `StateField`, a transaction filter, and — for desk-only ratchet — the *rearrangement rule*: a transaction whose removed and inserted "material" (non-whitespace, non-`~`/`%` characters, sorted) is equal and non-empty is a move, not an edit, and is allowed. That one rule powers sentence-shift, Shuffle write-back, and Selection Focus without per-tool exemptions.

**CodeMirror gotchas** (all learned the hard way):

- **Never put vertical `margin` on a CM block or block widget** — the heightmap measures `getBoundingClientRect` (excludes margin) and stores the margin as a `WidgetBefore` pseudo-block, which breaks ArrowUp motion past it. Use `padding` or fixed `height` (see `project-view.js`, `tab-marker.js`).
- **Block decorations cannot come from a ViewPlugin** — provide them via `EditorView.decorations.from(stateField)` (table renderer, inline panes, properties).
- **A menu floating over the editor must commit on `pointerdown`** — the gesture's first event, and the only one guaranteed to arrive while the row is still in the document. Pressing a row moves focus out of the editor, and anything that tears the menu down on blur removes it before the press finishes. `click` is far too late; **`mousedown` is also too late on iOS**, where WebKit delivers the compatibility mouse events hundreds of ms after `touchend` — long after the tap's blur has closed the menu. Spellcheck's suggestion popover failed this twice over, first on `click` and then on `mousedown`: picking a suggestion did nothing at all on iPad. Commit on `pointerdown` with `preventDefault()` (which also keeps the caret in the editor, so focus-gated decorations stay painted), keep `click` only for keyboard activation (`detail === 0`), don't let a blur arriving inside the press window tear the menu down, and swallow the one trailing `mousedown` — with the menu gone it lands on the editor and drags the caret off whatever was just committed.
- **Reveal-on-cursor decorations key off *containment*, not overlap.** A link, wikilink or citation drops its replace-widget and shows raw markdown while the selection sits inside it (`c.from >= from && c.to <= to`) — a caret in it, or a range picking out part of it. Testing for overlap instead meant every link inside a larger selection expanded at once, so selecting a paragraph reflowed it under the user's drag. The reveal exists so a link can be edited; a link merely swept up in a selection isn't being edited.
- **A ViewPlugin's decoration set is not mapped for you.** A plugin holding ranges computed from an async pass — spellcheck, proofread — must map both its own decorations *and* the offsets it built them from (`decorations.map(update.changes)`, `changes.mapPos`) on every `docChanged`, or every mark past the caret sits at a stale offset while the user types and only snaps back when the debounce re-runs. `from` maps with assoc `1` and `to` with `-1`, matching how a mark decoration maps itself: text typed against a word's edge lands outside the underline, text typed inside it extends it.
- **Overlapping replace/fold decorations crash the view layer** — filter candidates before applying (`applyFolds`).
- A caret inside a folded range auto-unfolds it — park the cursor at the fold start when folding would strand it.
- **No layout reads or dispatches inside `ViewPlugin.update`** — defer via `queueMicrotask` with a re-entry guard (wikilink decorator).
- Replace-decoration **widgets render outside surrounding mark spans**, so focus-mode dimming must be baked onto widget DOM (links, citation pills) and rebuilt on toggle.
- `EditorView.scrollIntoView` via `coordsAtPos` silently no-ops for offsets outside the rendered viewport — dispatch the scroll **state effect** instead (outline jumps).
- Widget teardown races taps on iOS — see Platform gotchas.
- A `getBoundingClientRect` read flushes CM's pending measure pass — some scroll-sync code (gutter) depends on that side effect; "optimizing" the read away breaks fresh-line measurements.

**Editor geometry**: column width is `paddingLeft/Right` on `.cm-scroller`, managed by `editor/modes.js#applyColumnLayout`, which also subtracts docked-pane footprints and reacts to sidebar/pane changes via `state.runtime.columnResizeHandler`. The bottom typing runway is `padding-bottom` on `.cm-content` — WebKit doesn't count a scroll container's own bottom padding as scrollable overflow. The doc's right-hand bars (outline, comments) carve their share of that column out too, and both are drag-resizable: `ui/side-panel-resizer.js` owns the strips, writes the live width to `--right-panel-width` / `--comments-panel-width` on `<html>`, and persists to `outlinePanelWidth` / `commentsPanelWidth`. Read those widths through `sidePanelWidthPx` — the constants they replaced are exactly what drifts the moment a bar is dragged.

## Styling / theme pipeline

Themes are plain data files under `src/themes/` (`themeList`, `getActiveTheme()` resolves style + appearance). Styles (named presets: theme, font, sizes, per-appearance color overrides, cursor mode, line indicator, background layers, shader layer) apply through **`style-application.js#applyActiveStyle`**, which writes CSS custom properties on `<html>` and emits `theme-changed` last. **All colour resolution goes through `theme-colors.js#resolveEffectiveColors`** — one chain (style override → style's resolved theme → global appearance theme, with the Default style's `defaultLight/DarkColors` standing in when no style is active) shared by the editor writes and the sidebar/chrome writes (`updatePrivateBoxColor` → `--theme-bg`, `--fg`, `--panel-bg`, …). Do not add a parallel resolution path: the sidebar-desync bug existed because the sidebar, editor, and panes each hand-copied this chain and drifted. The style hover-preview is the only caller that passes explicit override colours.

Every colour swatch in the style editor is routed to the in-app picker (`ui/color-picker.js`) by one `installColorPickers(modalRoot)` call: the native `<input type="color">` stays in the DOM as the value carrier (callers keep reading `.value` and listening for `input`/`change`, and it keeps painting the swatch for free, including when a section assigns `.value` from outside), wrapped in a span whose transparent hit layer opens the popup instead. A MutationObserver picks up inputs added by a re-render, so no section wires anything. The popup holds its own HSV: black and white carry no hue or saturation, so re-deriving from the hex every drag frame would collapse the pointer the moment it touched an edge of the field.

**Post processing** (`post-layers/`) is a layer stack, mounted with the same discipline as background layers: the entire runtime is `import()`ed only when a style with an enabled post layer applies, and `window.__hushPostLayerPanicCleanup()` tears down every artifact regardless of internal state. Seven effect types, all CSS (no canvas, no rAF): vignette / scan lines / tint paint their slot and blend; grayscale / sepia read their backdrop through `backdrop-filter`; glow puts a `text-shadow` on the real glyphs via an injected rule + scope class; opacity fades `<html>` itself, which the transparent Tauri window turns into genuine window translucency.

**Each post slot is a sibling in the root stacking context, not a child of one host** (z 501+, above the modal backdrop at 500 and below modal content at 510). A positioned host would be its own stacking context, and both `mix-blend-mode` and `backdrop-filter` inside it would sample that host's empty backdrop rather than the page — every effect would come out a no-op or a black wash. Ordering is paint order, so a grayscale layer above a tint greys the tint too. The scoped preview relies on the same rule from the other side: `.style-modal-preview` carries `isolation: isolate` so a previewed blend or filter samples the pane and stops there.

**Background layers** (`background-layers/`) follow the same lazy-import discipline. A style's `backgroundLayers` array (index 0 = back; types `image` / `gradient` / `webgl` / `caret`) mounts as a `#background-layers-host` div inserted as the editor element's first child, with the host's `z-index: 0` making it the isolation boundary for the layers' `mix-blend-mode` (the scroller sits above at `z-index: 1`). **The backdrop colour is passed in explicitly** (`backdropColor`, the same value just written to `--bg`) rather than picked up via `background: inherit` — `.cm-editor` is transparent under plenty of theme/style combinations, and blending against a transparent backdrop silently turns every blend mode into a no-op or a black wash. `backgroundLayersEnabled === false` switches the stack off without discarding it.

Legacy shapes never rewrite themselves at apply time. `styles-panel-shared.js#resolveBackgroundLayersList` derives layers from the old single `backgroundImage`, from a WebGL2 `shaderLayer`, and from the first-cut caret-knobs-on-a-WebGL-layer shape on the fly; `resolvePostLayersList` splits the retired single-overlay `shaderLayer` (which bundled vignette+scanlines or glow+scanlines behind one picker, under one master intensity) into one post layer per look, baking that intensity into the knobs it scaled; `normalizeCaretLayer` maps retired presets, folds the old caret `intensity` into the per-appearance opacity, and splits the single `blend` per appearance. `migrateStyle` bakes each conversion onto the style only when it's opened for editing.

Caret layers sample `EditorView.coordsAtPos` through an event-driven, rAF-coalesced tracker (`caret-tracker.js`, refcounted singleton) and hand shaders a short trail of `(position, birth, seed)` uniforms so particles are pure functions of age. A preset that needs more than the trail also gets the live caret (`u_caret` / `u_caretH`) — that's what the flicker bar rides. Idle behaviour is per-preset (`PARK_MODES`): trail presets (sparks, underline) clear and park once everything has faded, and `run` presets (flicker bar) animate whenever a caret exists. Parked loops wake on a 4 Hz caret poll, so an idle editor pays no per-frame cost either way. In a scoped preview there is no editor caret, so the runtime substitutes a pointer-following source that idles into a slow orbit.

A caret layer resolves **colour, blend mode and opacity per appearance**. Colour is `lightColor` / `darkColor` (with the pre-split single `color` as the fallback for both), or tracks the caret itself when `matchCaret` is set — which reads the live `--cursor` custom property off the layer's host rather than duplicating the colour chain. That works in the modal too because `updatePreview` publishes the draft's resolved caret colour onto the preview pane, so the layer inherits the *draft's* caret rather than the app's. Blend is `lightBlend` / `darkBlend`, defaulting to multiply and screen: these effects are drawn as light on a dark ground, and screen — the only mode that reads in dark mode — returns white for *any* colour composited onto a light page, which is why the colour pickers used to look inert in the light half. A pre-split single `blend` therefore seeds the dark side only; the light side always starts from multiply, because the stored value is the one that was invisible. Underline Glow draws capsules between consecutive trail entries rather than a blob per entry, so the stroke is continuous; entries join on distance (same baseline, within 160px) rather than on a tight time window, because gapping on time breaks the bar into dots the moment someone types at a human pace. Its coverage combines with `max()`, not `+=`, or the overlaps at each join would read brighter than the run.

The caret canvases render at the **display's own pixel ratio** (capped at 2), with an optional supersampling pass on top (`antialias`, capped at 3 and trimmed by an ~8M-backing-pixel budget that may only shave the bonus, never drop below the device ratio). They used to cap the ratio at 1 to halve fill cost — reasonable for a bloom blob, wrong for anything with an edge: on a Retina display every layer rendered at half resolution and the compositor upscaled it, so every preset came out blurry and about twice as thick. Every shader size is written in CSS px and scaled by `u_px` (backing px per CSS px), so changing the render scale changes sharpness, not geometry. Each preset also bbox-rejects trail entries that can't reach the fragment, which is what keeps the extra resolution affordable.

The caret canvases draw with **blending disabled**. Each preset writes one quad over a freshly cleared transparent buffer, so straight `(colour, alpha)` output is exact; the `SRC_ALPHA` blend they originally used squared alpha against a non-premultiplied canvas, which double-darkened faint output and turned every designed fade into its own square (an `exp(-0.85t)` tail displaying as `exp(-1.7t)`). Note what that squaring was hiding: every gaussian's outer half was invisible, so the presets read as small tight marks. Removing it made those halos appear and the same numbers rendered as huge soft blobs — the presets had to be retuned around the corrected maths (tight radii, hard falloffs, low alpha ceilings, `max()` rather than `+=` where shapes overlap). If you change the compositing again, re-tune every preset with it.

There is a floor on how thin a mark can usefully be, and it is not zero: a gaussian narrowed past about 0.5 CSS px of sigma spends all its brightness on the falloff, and once the supersampled buffer is downsampled the shape dissolves into a dotted line or vanishes outright. Small marks are therefore drawn as **hard shapes with a one-pixel `smoothstep` edge** rather than as shrunken gaussians — a disc for the spark motes — which holds full alpha in the middle at a 1-2px width. Gaussians are still right for anything wide enough to carry one (the underline's glow).

Each preset clamps its **coverage** to `[0,1]` and only then scales it by its own tuned alpha ceiling — clamping after the scale lets a preset whose coverage exceeds 1 saturate against the ceiling and flattens the top of its range. There is no brightness uniform: the effect's old `intensity` knob and the layer's per-appearance opacity were two controls that multiplied into one result, so intensity is gone and the opacity pair on the slot element (exactly as for image and gradient layers) is the only dial. `normalizeCaretLayer` folds any stored intensity into that pair, so an existing style renders at the brightness it always did.

Both stacks preview scoped to the modal's preview pane under their own `setScopedPreviewLock`, which makes editor-context applies no-ops until the modal closes (the modal's own live saves emit `style-changed`, which would otherwise steal the layers back to fullscreen mid-edit). The post stack takes its lock *unconditionally* on bind, even for a draft with no post layers: its slots cover the whole window, so leaving the active style's grayscale or half-faded window painted over the editor you came to tune is not an option — the background stack lives inside the editor element, hidden behind the modal anyway, and can skip that.

The list chrome for both sections is one module (`sidebar/style-layer-ui.js`): rows, grip drag-reorder, eye, delete, add buttons, and the per-appearance opacity pair. Each section supplies only a `describe(layer)` for the row, a `makeLayer(type)`, and its own option blocks. Rows reorder by dragging their grip; the drag listeners sit on `document` rather than on the grip under a `setPointerCapture`, because relocating the row mid-drag counts as a remove-and-reinsert and drops the capture, so the `pointerup` that commits the reorder never arrives.

## Panes

`pane/` is split around **`pane-state.js`** (the shared `panes` Map + accessors) so siblings avoid circular imports; `pane-manager.js` owns lifecycle and public API. Pane editors come from `createBaseExtensions`, so they behave identically to the main editor; inactive panes are locked non-editable and `pointer-events: none` to prevent input leaks. **What a CodeMirror theme can't carry, the container class must.** Cursor mode and the line indicator are classes on the host element, not editor extensions, so `createPaneEditor` binds both to its container (`bindCursorModeToContainer` / `bindLineIndicatorToContainer`, each returning an unbind the pane's `destroy` calls — panes and stack columns churn, and a listener closing over a detached container holds the whole surface). `applyBlockCursor` only ever reached `#editor-container` and the two overlays, which is why block and underline carets stopped at the pane's edge; the shared painter now stamps a `cursor-mode-surface` marker on whatever root it paints, so one CSS rule covers every host and clears the base theme's own `.cm-cursor` rule on specificity. The pane feeds the binding its *locked-style-resolved* settings (the same object `reconfigureTheme` builds), so a doc with a locked style gets that style's caret rather than the session's. **The line indicator's margin marks have a second geometry for these hosts**: `createBaseExtensions` takes `flushLineIndicator`, which panes and stack columns set. The main editor hangs the arrows and border stripes 13-18 px outside the text column, into the gutter `applyColumnLayout` leaves; a pane has no such gutter and clips at its rounded border, so those offsets cropped the marks away entirely. Flush mode spans the overlay across the scroller's own box and pulls the marks inside its edges — the indicator attaches to the pane's edge, and the highlight wash runs edge to edge. Every surface also paints its indicator whether or not it holds focus, going grey (`hush-line-ind-muted`, resolved through one `--line-ind-paint` swap) when it doesn't — the same two-state colouring the pane border uses, so a stack of three docs shows where the cursor sits in each without three of them claiming to be live. Content sync with the main editor is bidirectional under a pull-lock flag with try/finally guards; `pane-external.js` is the other direction — externally-changed bytes arriving from a synced desk folder, applied per pane under its own dirty flag (see README-SYNC).

**`savePaneContent` must read its surface synchronously.** `closePane` fires it without awaiting and tears the pane down on the next line, so anything read after the function's first `await` is already gone. A notebook pane used to encode *after* awaiting the codec import, found `pane.notebook` null, threw into the catch, and silently dropped everything drawn since the last autosave. It now gathers the whole envelope up front, and a save that couldn't read its surface at all refuses to write rather than truncating the file to an empty string.

**Docking** (`pane-dock.js`) is a contract between panes and every host surface: docked footprints publish as CSS vars (`--pane-dock-{left,right}-width`, `--pane-dock-{top,bottom}-height`, `--pane-dock-*-edge`) plus a synchronous `pane-dock-changed` document event; containers consume the vars in pure CSS, and `editor/modes.js` copies the event payload onto `state.runtime.docked*` in the same frame (the lazy-import path could resolve after paint, flashing the editor under a fresh dock). The four edges carve mutually exclusive territory; `publishDockCssVars` skips `display:none` panes so an inactive context's dock can't leak its footprint. **iPad chrome keys off the dock edge, not off "is this a pane"**: a dock that reaches the top edge (left / right / top) floats its title bar as a centred pill clear of the system menu band, and one that reaches the bottom edge (left / right / bottom) pads a PDF viewer's toolbar out of the grab-handle + ☰-pill band exactly as the main viewer does. Both are pure CSS on `.docked-<edge>`, so undocking reverts them in the same frame. The pill also reserves a 30 px strip of bare bar between the filename and the buttons: it shrink-wraps its contents, and `setupPaneDrag` bails on both the title link and every button, so without the strip a docked pane had no grabbable title bar at all.

**Gutter** (`project/gutter.js`) is a docked notebook pane scroll-locked to a doc: the dock module owns geometry, and the canvas camera is slaved to the editor scroll (`camera.y = offset − scrollTop`, `zoom` locked at 1, so world-y ≡ doc-content-y). The doc↔gutter pairing is a **naming convention** (`<docName>-gutter` inside the doc's project), re-derived from names on every render — it survives round trips, restarts, and the `.hushproject` envelope with no metadata field. When serializing a gutter pane's notebook, the *pre-gutter* camera snapshot is written, never the live scroll-tied one (a scroll-position camera persisted into the file would seed the main canvas at a bogus viewport later).

**A pane holds the whole file, so a pane's save writes the whole file.** A notebook pane hydrates through `loadShapes` with the same extras the main canvas gets (splits, proof metadata) and encodes every field back on save — the same for stack columns. Anything the load skips, the pane's own autosave deletes from disk minutes later: that is how bookmarks were lost once, and how a proofread notebook opened in a pane used to come back as a plain notebook. **Canvas chrome that positions against the window must branch on `state.paneHosted`** (`shelf-panel`, `proof-thumbnails`, `proof-scrollwheel`, `toolbar`, `bg-settings-fixed-button`): a pane's edges are interior, with the safe-area bands and dock footprints already carved out by its host. Applying the window form inside a pane isn't a cosmetic slip — **the global right-dock width IS a right-docked pane's own width**, so the shelf was pushed a full pane-width inboard, out of the pane entirely, and the `rightInset` the canvas measures from it (now clamped to the canvas width) then fed a nonsense number to everything that parks against the shelf: the page rail, the toolbar's centring, the drawing panel's pill. One escaped element took the whole surface's chrome with it. `state.hostTopInset` is the other half — the pane's own floating pill title bar, measured from geometry by `pane-dock.js#syncPaneChromeInset` (the overlap of the title bar's box past the top of the content box, which is 0 for an in-flow bar) so top-pinned chrome lands beneath it.

**Persistence**: the open pane set (geometry, anchoring, per-pane view state — editor scroll, PDF zoom, notebook camera) rides `.hush/panes.json` with a 300 ms debounce; position stays per-device. Inline panes anchor as `{ anchorTitle, occurrence, height }` under the Nth `[[wikilink]]` occurrence.

## Notebooks, Desktops, Drawing

See [README-NOTEBOOK.md](README-NOTEBOOK.md) and [README-DRAWING.md](README-DRAWING.md). The contracts that matter from outside:

- The canvas is mounted/unmounted by `notebook-bridge.js` with **serialized lifecycle** and multiple guards against saving an empty canvas over a real file — don't bypass `saveNotebook`.
- **Shapes are immutable once in `state.shapes`** — mutations replace objects. The sync shim's identity diff and the undo manager's structurally-shared checkpoints both depend on it.
- Notebook files are a versioned JSON envelope (`notebook-content.ts`); `.hushnote` zip packing (`sync/notebook-sync.js` / Rust `hushnote.rs`) is the only wire format. **Both codecs pass the envelope through whole** — the only field either knows is `shapes[].dataUrl`, which is what gets extracted into the zip's `images/`. Never re-assemble the envelope from a named field list: the JS half did that twice, and each time the fields that existed on the day it was written survived while every field added afterwards (camera, background, bookmarks, splits, `proof`) was silently deleted on the next save. The same rule binds anything else that builds an envelope — the `.hushnote` export encodes through `encodeNotebookContent` for exactly this reason.
- **Splits are not shapes.** They're a notebook-level list (`DrawingState.splits`) with their own envelope field and their own slot on the undo checkpoint, so they never touch the `Shape` union's bounds / hit-test / clipboard surface. **Grabs** ride the checkpoint too (`NotebookCheckpoint.grab`) — that's what makes ⌘Z after placing a grab return to the place stage rather than unwinding the whole two-stage operation.
- **Create Proofread Notebook** (`pdf/pdf-proofread.js`) produces an ordinary `.hushnote` with an extra `proof` envelope field; nothing downstream branches on it except the page rail (a live minimap of the page layer plus a sketch of the annotations over it) and the shelf, which hides the page layer. The tree node carries a `proofread` flag purely so the sidebar can pick a different glyph — the real metadata lives in the notebook. Zotero marks are baked into each page raster by `pdf/pdf-annot-raster.js`, shared with the shelf-cover baker: Zotero annotations are attachment child items, not PDF content, so pdfjs renders a clean page and anything rasterizing one has to paint them itself. (Annotations embedded in the PDF *file* need no help — pdfjs's default `annotationMode: ENABLE` draws those into the canvas.)
- **Save to Desk** (`pdf/save-pdf-to-desk.js`) is the export modals' alternative delivery for PDF output: register a placeholder, write the binary, let the cover follow. The result is indistinguishable from an imported PDF, which is the point — the export/annotate loop shouldn't need a round trip through the file system. Image-heavy notebooks (a proof is fifty full-page rasters) fall under `notebook/image-budget.ts`, which keeps only images near the viewport decoded.
- Desktops (`desktop/`) reuse the whole notebook engine with per-canvas capability switches on `DrawingState` (`flowchartEnabled`, `flowEdgesLocked`, `desktopMode`, …) and store per-device layout/thumbnail caches in IndexedDB — a pattern to follow for future canvas-based takeover views.

## Multi-window

Desktop and iPad (native scenes, Tauri ≥ 2.11). A Rust `WindowRegistry` tracks `{ label, fileId, fileType }` per window; windows register at boot, push their open file, heartbeat every 4 s (mobile entries expire after 10 s of silence — iPad scene teardown can be completely silent, and closed vs switcher-parked scenes are indistinguishable), and are pruned belt-and-braces (destroy events, JS `beforeunload` + `pagehide`, reconciliation against live webviews). Native titles (`[Desk]-[File]`) go through `set_window_display_title`, which on iOS walks to `UIWindowScene.title` for the app switcher.

Cross-window sync: `broadcast_state_change` (settings / files — receivers re-fetch from disk and merge), `broadcast_doc_changed` (live buffer, debounced 250 ms), `broadcast_notebook_changed` (**id only** — the envelope is multi-MB and marshalling it froze the saving window). Receivers apply under the pull lock so echoes can't loop. Two hard-won rules:

- **Every settings write is key-scoped**, through Rust's `patch_settings` — the caller sends the keys it changed and nothing else, and the merge happens under the settings mutex so concurrent patches can't interleave. A window's in-memory copy is stale the moment anything else writes (a sibling window, the Settings panel's snapshot from when it was opened, another write from this window still in flight), and sending a whole `AppSettings` asserts a value for every setting in the app, last write wins. That is how the YOUAREHERE registry vanished, and later how a closed floating pane came back on the next launch — intermittently, both times, because it turned on which write landed last. `save_settings` (whole-object) stays registered only so a stale web bundle on a fresh binary keeps working. Per-window keys (`lastFileId`, `scrollPosition`, `activeDeskId`, mode flags, sidebar chrome) run the other way: disk holds the *main* window's session, so a secondary window keeps them in memory and never writes them at all.
- Subscribe to cross-window events **before** registering, so the registration's own broadcasts arrive through the same pipe.

`activeDeskId` is per-window: each window operates its own desk; only main's choice persists as the launch desk.

**Sticky notes are per-window too, and nothing in their model says so.** A sticky is scoped to a file / project / desk / the app, and every window with that scope open drew its own copy — the same reminder twice, both editing one settings-backed list. `sticky/sticky-window-claims.js` settles it without a clock or an arbitration round trip: each window broadcasts the note ids it *could* show (`broadcast_sticky_claims`) along with its registry number, and a note belongs to the lowest-numbered claimant. Registry numbers are minted in window order and never reused, so "the window that already had it keeps it" falls out of the ordering, and every window computes the same owner from the same facts. The one timing-sensitive part is boot: a window that starts beside a lower-numbered sibling hasn't heard its claims yet, so it shows nothing until every such sibling has answered (its own announcement is what prompts them) or 1.5 s passes. Claims are dropped on `windows-updated` when their window leaves the registry — that is what hands a note back when the window holding it closes.

**Scene triage (iPad).** Not every `UIScene` iPadOS offers is a window the user asked for. `ios_scene.rs` classifies each `RunEvent::SceneRequested` by session role and only builds for the application role; external-display and unknown roles are refused and logged. See Platform gotchas for the three-part external-display refusal and the `setFocus` trap that used to mint scenes by accident.

**Diagnostics.** `src/window-diagnostics.js` writes the window's geometry, screen, pixel ratio and safe-area insets to the activity log at boot, then a diff whenever any of it moves (coalesced 400 ms — a Stage Manager drag fires `resize` continuously), plus visibility / focus / freeze / `pagehide` transitions and every registry change. The Rust side logs scene decisions, window destroy/close, display-scale changes and `Suspended`/`Resumed`. Settings → Debug → **Windows & Displays** shows the live picture and has a button that writes a snapshot into the log. A trail that ends on "suspended" and resumes at a fresh boot is the OS reclaiming the app; one that just stops is a crash — that distinction is the reason the lifecycle lines are there.

## Startup

**The window is transparent, so every millisecond before first paint is a black screen.** There is no OS-drawn launch image standing in: the surface behind a transparent `WKWebView` is a `UIWindow` with no background colour, `base.css` leaves `html, body` transparent, and the `html.ios` rule that would paint it only applies once `main.js` has added the class — which is a whole `AppState.init()` away. A launch that takes five seconds looks like five seconds of nothing, and looks the same whether the app is doing real work or is wedged.

Three pieces address that, and they are deliberately separate:

- **The splash** (`index.html`) — inline `<style>` plus an inline SVG of the menu-bar mark at 200 px, pale on black, painted from the document itself so it does not wait on the app's CSS or its JS. It fades the mark in on a 140 ms delay, so a launch that beats the delay shows plain black and never flashes an icon. `main.js#revealApp` takes it down one frame after the first surface is mounted; `window.__hushHideSplash` is also called from `init()`'s catch and from a 15 s timer in the document, because a splash that outlives a failed boot is worse than no splash.
- **The trace** (`src/startup-trace.js` + `src-tauri/src/startup_trace.rs`) — a named phase per step, both halves of the launch. Recording is unconditional (two clock reads and an object per phase); the `trackStartupTiming` setting gates only whether the run is *written* for the settings webview to read.
- **The panel** — Settings → Debug → **Startup Time**, top of the tab. Toggling it on asks the editor window (via `hush-startup-timing-capture`) to persist the launch already in progress, so the list fills in without a relaunch.

### What a launch actually does

Native, in `run()`, with no window on screen and nothing on the JS side able to observe it: data dirs created → `AppSettings::load` → `migrate_from_flat` → `migrate_snapshots_db` → managers constructed → `snapshot_manager.cleanup_all()` → (in `setup`) local-sync watchers re-armed → `reconcile_desk_registrations` → desk watchers armed → `refresh_gdoc_link_cache` → recovery scheduler → window shown.

Webview, in `main-boot.js#bootAppState` then `main.js#init`, every step awaited in series: window label → wikilink hooks → activity log → window diagnostics → (iOS) re-acquire security-scoped desk folders → **`AppState.init`** (`get_settings` → `list_files` → `get_file_tree` → legacy-tree migration → special nodes → PDF layout normalise → PDF registry → prune empty Untitled → restore last file) → seed style presets → appearance CSS vars → `createEditor` → text/image drag → `setupModeSwitching` (mounts the first surface) → `createSidebar` → floating panes → **reveal**.

### Where the time goes

Ranked by cost. Item 1 is measured — on an iPad it was 2.8 s of a 3 s launch — and is fixed; the rest are ranked by expected cost, with byte counts from a production `vite build`. Read the Startup Time panel on the actual iPad before acting on the order of what's left.

1. **`list_files` used to read the entire library, byte for byte, before anything painted** — 2.8 s of a 3 s iPad launch. It walked every desk index and called `read_at` on every entry: every `.md`, and every `.hushnote` through `hushnote::unpack`, which inflates the zip, base64s each embedded image back into a `dataUrl` and re-serialises the envelope. Images were read too, whole, and then dropped when `read_to_string` rejected their bytes.

   Almost none of it was ever read back. `state.files` is two things wearing one name: a **library index** (id → name → mtime) that thirty-odd call sites use, and a **content cache** that, under Tauri, exactly three call sites touch — the sidebar's tab/heading rows, the boot-time empty-`Untitled` sweep, and the wikilink rewriter. The first two want documents. Every other consumer already went to `load_file`, including the one that opens the document you're looking at.

   A synthetic library measured with the real codec says how lopsided that was:

   | kind | files | read | returned |
   |---|---|---|---|
   | documents (4 KB `.md`) | 400 | 2.6 ms | 1.54 MB |
   | notebooks (2 MB of strokes) | 6 | 1.1 ms | 2.24 MB |
   | notebooks (proof, 50 rasters) | 2 | **119.5 ms** | **26.05 MB** |
   | images (500 KB `.png`) | 60 | 5.1 ms | 0 MB — every read failed |

   Documents were 2 % of the read and 5 % of the payload. The other 95 % then had to be JSON-parsed by the webview's JS thread before boot could continue, which is where an iPad turns a hundred milliseconds of decode into seconds of black screen.

   **The listing now reads documents and nothing else** (`FileManager::list_files`, returning `FileSummary`). Notebooks and stacks get a `stat` and arrive with `content: null` — deliberately null and not `""`, because an empty body reads downstream as a deletable placeholder. Images are skipped by extension without being opened, which is what already happened to them, just without the read. The two consumers that wanted documents are unaffected; the third, the wikilink rewriter, moved to Rust (below).

2. **The entry point drags in 224 modules before `init()` runs.** `index.html` ships 68 preloaded chunks — **1.31 MB of minified JS and 347 KB of CSS** — all of which must be fetched, parsed and compiled before the first line of `main.js` executes. Much of it is meant to be lazy and isn't. One edge does most of the damage: `editor/base-extensions.js` imports `editor/commands.js` for the keymap, `commands.js` imports `command-palette.js`, and the palette pulls in `command-palette-commands.js` (41 KB) and through it sticky notes, the gutter, `state-tree.js` and the pane manager. A second edge does the rest: `commands.js` → `find-replace.js` → `sidebar/find-panel.js` → `notebook-bridge.js` → `notebook-content.ts` → `flowchart.ts`. That is why `main.js`'s own `import("./sticky/sticky-notes.js")` buys nothing — the module is already in the entry chunk. Rolldown says so out loud on every build (`INEFFECTIVE_DYNAMIC_IMPORT`, three of them today); those warnings are a to-do list, not noise. **Fix:** put the seam where the graph narrows — have the keymap resolve command handlers through a registry populated on first use rather than importing them, and give `find-replace` a lazy path to the find panel. Cutting the palette and the versions/find panels alone drops 16 modules and 203 KB; cutting the notebook and Zotero reach from the editor's keymap takes considerably more.

3. **Boot is one long serial `await` chain.** Nothing overlaps and nothing is deferred past first paint. `get_settings`, `list_files` and `get_file_tree` are three sequential IPC round trips that have no dependency on each other. The style-preset seed, the PDF registry, the empty-Untitled sweep and the local-desk-folder re-acquire all block the editor from being constructed, and none of them is needed to show a document. **Fix:** `Promise.all` the independent reads; move everything that isn't "settings + the tree + the one file we're opening" to after `revealApp`.

4. **`snapshot_manager.cleanup_all()` runs synchronously in `run()`, before the window exists.** It walks `.hush/versions/` for every desk, lists every snapshot of every document, and deletes what the decay policy retires. On a synced folder, where `read_dir` may be hitting provider placeholders, that is unbounded — and it is housekeeping with no deadline. **Fix:** hand it to a background thread after the window is up, the way `desk_recovery::start_scheduler` already does.

5. **`initPdfRegistry` awaits one IPC round trip per PDF.** `for (const fileId of ...) await checkPdfExists(fileId)` — strictly sequential, and a `pdf_exists` per entry. A library with a hundred PDFs pays a hundred serialized crossings before the editor is built. **Fix:** one batched `pdf_exists` command over the whole id list; and move the whole registry init off the pre-paint path.

6. **355 KB of render-blocking CSS, carrying 217 `@font-face` rules.** The font *files* are not fetched at boot (205 of the rules carry `unicode-range`, and WebKit only pulls a face when a glyph needs it), but the stylesheet is a hard render block — nothing paints, splash included, until it parses. **Fix:** split the sheet into a small critical file (`base.css` + editor shell) linked in `<head>` and the rest loaded non-blocking; move `font-imports.js` out of the entry graph and into a deferred import.

7. **Small change, several times over.** `reconcile_desk_registrations` runs in `setup()` and again inside `load_forest`. `getCurrentWindowLabel()` is awaited three times in the preamble. (`pruneEmptyUntitled`'s second full `list_files` went with item 1 — it now filters its own cache.) None of these is the five seconds, but they are free to fix.

### Rules

- **Nothing goes on the pre-paint path that isn't needed to draw the first surface.** Settings, the tree, and the bytes of the one file being opened — that is the list. Registries, sweeps, seeds, watchers and caches belong after `revealApp`.
- **Never read the whole library to answer a question about one file.** `list_files` is the standing counter-example; treat a new call to it on any hot path as a bug.
- **`state.files[].content` is documents only, and `null` is not `""`.** Anything that needs a notebook, a stack or an image goes to `load_file`. A consumer that treats a missing body as an empty one will delete somebody's work — see the type guard in `pruneEmptyUntitled`.
- **A library-wide scan belongs in Rust, off the main thread.** `wikilinks.rs` is the pattern: substring-pretest before parsing, and for a `.hushnote` read `data.json` out of the zip (`hushnote::read_data_json` / `replace_data_json`) rather than `unpack`, which base64s every image the file holds.
- **Wrap new boot steps in `phase()`.** An unnamed step is one the panel attributes to its parent, which is how a regression hides.
- **Take `INEFFECTIVE_DYNAMIC_IMPORT` seriously.** Each one is a module the author believed was lazy and isn't; the fix is a seam, not a `/* eslint-disable */` of the build.

## Backend notes

- `AppSettings` uses `#[serde(rename_all = "camelCase")]` and `#[serde(default)]` on every field; defaults live in `settings/defaults.rs`.
- Images: binaries live in each desk's `Images/` under the original filename (auto-suffixed); **the filename is the fileId**; reads search every desk (markdown refs are bare filenames); saves land in the active desk.
- The `[@` citation picker opens on the citation **being typed**, which the backward scan from the caret can't tell from one already written — `[@smith2020](zotero://…)` looks identical behind the caret to `[@smith2020` still being composed. `findActiveCitationContext` therefore also runs *forward* to the end of the citekey and bails if a `]` closes it, so arrowing through a finished citation expands it like any other link instead of reopening the picker and taking the caret with it.
- Zotero caches (`zotero_references.json`, `zotero_collections.json`, `zotero_pdfs/`, `zotero_annotations/`) are local-only, never synced; PDF fetches happen server-side (`reqwest`) because Zotero's `/file` 302s to a presigned S3 URL whose CORS rejects the webview's `null` origin. Annotation fetches use the `/children` endpoint — `/items?parentItem=` does not actually scope and returns the whole library.
- `typst_export/`: citations are folded to control-char sentinels before pulldown-cmark (split-text events would lose bracket framing) and expanded per `CitationMode`; emphasis/cites emit Typst's *function* forms (`#emph[…]`, `#cite(...)`) because the markup forms are whitespace-sensitive (`*shape*attention` breaks). The in-memory `World` carries fonts from `typst-assets` + bundled Karla; no package resolution — iOS can't reach the network at render time.
- **Typst raw closes at the first matching backtick run**, so `typst_export/code.rs` fences a block one backtick longer than the longest run inside it and sends inline code carrying a backtick through `raw("…")` instead. Get this wrong and the failure lands nowhere near the cause: the raw closes early, every paragraph after it parses as Typst code, and an ordinary `#tag` hundreds of lines later comes back as "unknown variable: tag" with the whole export lost.
- **Typst fails the whole compile on anything it can't resolve**, so the converter never emits a reference it can't back: an unknown citekey becomes a red `[@key]` marker (`citations::missing_cite_marker`) and an image the store couldn't produce bytes for becomes its own markdown in red (`images::emit`, driven by the set of filenames that actually reached `ExportWorld`). A remote `http(s)` image is the same case — the World has no network. Degrade the rendering, never refuse to render.
- Per-export knobs ride `styles::WrapOptions` and are emitted around the style's preamble, not inside it. `heading_space` is a `#show heading:` rule emitting **weak** `v()` spacing, which is what lets it compose with each style's own `heading.where(level: N)` rules (and any style added later) and collapse at page tops; it emits nothing at all at 0, so an untouched export is byte-identical to one from before the option existed. `typst_export::tests::heading_space_pushes_content_down` asserts the composition by page count — a shadowed show rule would compile cleanly and change nothing.
- Grammar (`harper-core`) and spellcheck (`spellbook`) both run `async` + `spawn_blocking`; dictionaries embed via `include_str!` behind `OnceLock`.
- The activity log (`activity_log.rs` + `src/activity-log.js`) is the cross-window console: JSONL ring at `{data_dir}/activity.log`, JS batches on a 1.5 s timer with eager flush on error/`pagehide`/`visibilitychange: hidden` (iPad swipe-away never runs `beforeunload`). Rust logs fire-and-forget — diagnostics must never fail the operation they describe.
- Build stamps: `scripts/gen-build-info.mjs` (web) + `src-tauri/build.rs` (native) surface in Settings > Debug; a mismatch (stale bundle + fresh binary, common on iPad) explains many "impossible" bugs.
- `startup_trace.rs` records the native launch phases (settings load, the two migrations, snapshot cleanup, watcher arming) behind a `OnceLock<Mutex<Vec<Phase>>>`, read back by `get_startup_native_timings`. Same rule as the activity log: it must never fail the operation it measures.

## Platform gotchas (lessons learned)

### WebKit / iOS

- **`visibility: hidden` on a container + `visible` on a child is valid CSS that WebKit may simply never paint** — the element computes visible, composites, and isn't drawn until an unrelated invalidation. Hide siblings individually instead (Desktop panes).
- **The Canvas2D cost model on iPad** is upload-dominated: WebKit rasterizes CPU-side and uploads the canvas's *dirty region* at ~280 MB/s, so fully dirtying a visible 4096² canvas costs ~235 ms regardless of JS cost; a ~1 %-opacity canvas skips the upload; using a canvas as its own `drawImage` source forces a ~230 ms GPU→CPU readback; a *mutable* canvas as a draw source re-uploads per draw (promote to `ImageBitmap`); and assigning `canvas.width` reallocates the IOSurface (0.8–1.5 s) even for the same size — guard no-op resizes. The full story is engine deltas #25–#31 in README-DRAWING.md.
- **Production WKWebView leaves `var(--theme-bg)` chrome stale** after focus/visibility transitions — `updatePrivateBoxColor` force-writes inline backgrounds on the themed surfaces under `html.ios`, once synchronously and once next frame (the restore can clobber a synchronous write).
- **Cancelling `pointerdown` does not stop WebKit sending `mousedown`.** The spec says a cancelled `pointerdown` suppresses the compatibility mouse events; WebKit delivers `mousedown` for a mouse pointer anyway. That matters for chrome floating over an editor, because double-click word-select is `mousedown`'s *default action* and it fires even over a `user-select: none` element — it just widens whatever selection already exists. Double-clicking a sticky note's header to collapse it therefore selected the word under the caret of the pane underneath. Chrome that must not disturb a selection cancels `mousedown` itself, exempting only its own text inputs.
- **Tap → caret placement re-renders CM and tears down the tapped widget before `click` fires.** Open-from-widget handlers attach `pointerdown` directly to the widget element and capture anchor rects synchronously (an awaited import later, the element rect reads as zeros). Dismiss-on-outside listeners use `pointerdown`, not `mousedown` — iOS delivers the synthetic `mousedown` hundreds of ms after `touchend`, past any rAF that armed the listener, so a `mousedown` dismiss self-closes on the opening tap.
- **iOS fires `pointercancel` (not `pointerup`) when it claims a near-stationary touch for scrolling** — recover an in-slop cancel as a click or files need two taps to open. Multi-touch gestures end with paired `pointerup`s milliseconds apart — a pinch reads as a double-tap unless the detector tracks concurrent contacts and poisons the whole gesture (`pointercancel` must feed the same bookkeeping or the set leaks and locks the detector).
- **`beforeunload` never runs on iOS** — also flush on `pagehide` and `visibilitychange: hidden`.
- **iPadOS reclaims a backgrounded webview's content process**, and the page then *reloads from scratch* when you come back — a few seconds of black, then the app restored from disk. Every autosave timer stopped at background, so anything since the last tick that landed is gone: strokes, text, and the pan/zoom that rides the same envelope. A proofread notebook (fifty full-page rasters) is the hungriest surface Hush has, so it goes first. `state/background-flush.js` forces the notebook, doc, panes and stack columns to write on `visibilitychange: hidden` / `pagehide`, bypassing the notebook's quiet-moment gate and camera-only cap — those protect a gesture, and there is no gesture once the user has left. It logs before and after: a trail with only the "Flushing" line is a flush that was frozen mid-way.
- External-app drops on iPadOS often arrive via `dataTransfer.items` with `files` empty — union both sources and dedupe.
- **A ranged selection in editable web content is drawn twice on iPadOS** — CodeMirror's `drawSelection()` layer and UIKit's native selection view (the machinery behind the grab handles and the loupe). The native one is painted by the system, not the web process, so `::selection` — which is what hides it everywhere else — cannot reach it, and it shows through as a grey rectangle slightly out of register with the styled one. `tintColor` on the `WKWebView` is the only lever the platform offers; `commands/window.rs#set_native_selection_tint` points it at the live `--selection` colour (pushed from `theme-colors.js` beside the background colour, same objc walk, same dedupe) so the two layers read as one selection.
- **Toggling `contenteditable` resets the scroller under it in WebKit.** The subtree's render tree is torn down and rebuilt, and the scroll position goes with it. Panes flip `EditorView.editable` on every focus change, so a doc pane came back parked at the top of its document — and because the reset lands on the *blur*, the user only sees it when the pane is next focused, which makes it look like a focus bug rather than a blur one. `pane-editor.js#setEditable` holds the offset across the flip (once synchronously, once after the measure pass).
- **`navigator.clipboard.read()` under Tauri's WKWebView answers with the macOS "Paste from …" prompt, once per read** — and a paste event's own `clipboardData` routinely arrives empty for image bytes. Together that is why pasting an image into a Doc looked like it did nothing and pasting one onto a canvas took several tries: the bytes were only reachable behind a prompt the user never asked for. `src/clipboard-image.js` reads through `@tauri-apps/plugin-clipboard-manager`'s `readImage()` first (NSPasteboard directly, no prompt; desktop only — the plugin doesn't implement it on iOS), with the browser API as the fallback, and hands both consumers a PNG data URL. Two rules for callers: **start the read before any other `await`** in a paste handler, because the browser fallback needs the gesture's transient activation and an IPC text read is long enough to spend it; and **only use the result when the clipboard carried no text** — macOS offers an image representation of some rich-text copies, so reading unconditionally would paste a picture of the words in place of the words. **On iOS the plugin step is skipped entirely**: there is no `readImage` there, so trying it bought nothing and cost a dynamic module load plus an IPC round trip — spending the very activation the browser read then needed. That ordering, not the browser API itself, is why an image paste on iPad landed only every few ⌘V. The rule generalises: a fallback chain whose first link is known-dead on a platform is not free when the last link is gesture-scoped.
- **WebKit often answers an image paste with markup instead of bytes** — `clipboardData` carrying only `text/html` holding an `<img>`, with `files` and `items` empty. Where that `src` is `data:` or `blob:` the image is already in hand: `fetchableImageSrcsFromHtml` + `filesFromImageSrcs` (clipboard-image.js) take it with no permission, no prompt and no gesture, and the doc paste handler tries that route *before* the OS clipboard. The decision is made synchronously so that *not* taking it leaves the gesture's activation intact for the read that follows. A `webkit-fake-url:` src is WebKit naming bytes it deliberately kept back — unfetchable by design, and reported as such rather than as "nothing found". A rich-HTML paste that converts to an empty string is a refusal too, not a result: `paste-extension.js` returning `true` for `""` swallowed the whole event. And the two paste handlers no longer share a precedence — image paste is `Prec.high` in both extension lists, because which one CodeMirror offers the event to first should not be a property of array order.
- **The paste path narrates itself into the Activity Log** (Settings → Debug, filter `paste`): the event's types and payload sizes, which route was taken and why, what the clipboard read returned or threw (`NotAllowedError` from a spent iOS gesture is the one to look for), and whether `save_image` succeeded. Every one of those was a bare `catch (_) {}` before, which is why "the paste did nothing" arrived with nothing to read — and on iPad there is no console to fall back on. `paste-diagnostics.js` holds the two describers the editor and the canvas share.
- **`UIApplicationSupportsMultipleScenes` also opts the app into external-display sessions.** Plugging a monitor into an iPad handed Hush a second scene, which booted the app and restored the last file onto the monitor; the role is non-interactive, so the pointer couldn't reach it, nothing in the app could close it, and unplugging the cable was the only way out. Refusing that session takes **three** pieces, because no one of them covers the window the others leave open:
  - `tauri-plugin-scene-reuse` (Swift) destroys any scene whose session role contains `ExternalDisplay`, off `UIScene.willConnectNotification`.
  - `ios_scene.rs` (Rust) makes the same call from Tauri's `RunEvent::SceneRequested`, reading the role by `msg_send!`, and — crucially — **declines to build a window for it**. Tauri's own handler built one for every requested scene, so a monitor plugged in booted a full second copy of the app; three of them showed up in one session's log. The two halves run off different notifications with no ordering guarantee, hence both.
  - The Swift half also parks an **empty hidden `UIWindow`** in the scene before requesting destruction. Destruction is asynchronous, and tao's `create_window` hands each new window to the first connected scene with *zero* windows (`unitialized_scene()`) — so during those few hundred milliseconds an ordinary "Open in new window" would have its window adopted by the display we're declining.

  Application-role scenes are untouched, so a window the user drags to a monitor under Stage Manager still works.
- **Never call `setFocus()` on iOS.** tao's iOS `set_focus` activates a scene session from an *empty* `UISceneSessionActivationRequest` on iOS 17+, and an empty request is the API for "give me a new scene". Every focus call therefore came back as a `SceneRequested` — a spare window, a spare Hush entry in the Dock, and, with the old handler, a spare copy of the app. The fullscreen toggle and the Zotero deep-link import are the two call sites that used to reach it; both are now desktop-gated (`src/editor/modes.js`, `src/links/zotero-helper-import.js`). `ios_scene.rs` caps scene-built windows at 8 as the backstop.
- **A transparent window has a black hole under it.** Hush's window is `transparent: true`, and the surface behind a transparent `WKWebView` on iPadOS is a `UIWindow` with no background colour — i.e. black. Any moment the page isn't painting the whole window shows it: the seconds after the window changes display (plugging in a monitor is the reliable repro), a safe-area band mid-rotation, the gap before first paint. Resizing the window "fixed" it because that forced a repaint. Tauri's `set_background_color` documents itself as unimplemented on iOS, so `commands/window.rs#set_native_background_color` walks webview → `UIWindow` (plus the webview's own view and its internal scroll view, which paints over the window's) and sets the theme colour there. `theme-colors.js` pushes it on every colour change, deduped, and `installIOSChromeRepaint` re-asserts the CSS side on resize / rotation / pixel-ratio change — the display-change counterpart to the foreground-transition mitigation.
- **`scrollIntoView` scrolls every scrollable ancestor, including `overflow: hidden` ones.** A stack column's content box and the notebook wrapper inside it are `overflow: hidden` — user-unscrollable, programmatically scrollable — and outside them is the stack's horizontal scroller. The proof page rail called `scrollIntoView({ block: "nearest" })` each time the highlighted page changed, so reading a proof *down* scrolled its stack *sideways* and shoved the canvas out of its own wrapper, with no way for the user to put it back. Scroll the element that is supposed to move (`scrollTop` on the rail's own scroller); `pinUnscrollable` in `stack/stack-component.js` holds the hidden boxes at their origin as a guard for the next one.
- iPadOS deep links are delivered **more than once** (every window, replayed `getCurrent()`, webview reloads) — dedupe by nonce in a shared ring; and without `tauri-plugin-scene-reuse` the OS spawns a fresh empty scene per incoming URL.
- WKWebView's native scrollbar is a non-grabbable overlay on iPad — surfaces that need a draggable thumb build their own (stacks).
- `toDataURL("image/webp")` yields PNG on WebKit, WebP on Chromium — sniff magic bytes when reading caches back.
- Linking Google's ML Kit static archives with a global `-ObjC` flag detonates on Tauri's `libapp.a` (Swift objects embedded once per plugin) — the pod-install script rewrites to per-archive `-force_load` (`scripts/ios-add-mlkit-pod.mjs`).

### Tauri / OAuth / integration

- Tauri's built-in drag-drop is disabled (`dragDropEnabled: false`) so DOM drop events reach the webview.
- The macOS `#drag-region` strip (z 80, `-webkit-app-region: drag`) steals clicks from anything beneath it — chrome that must sit at the top edge either mounts at body level above z 80 (the Google link bar) or the region is display-noned for that surface (notebook/PDF/stack/Desktop takeovers). A child of a lower stacking context can never outrank it, no matter its local z-index.
- Google OAuth for desktop apps requires a **loopback HTTP redirect** (`http://127.0.0.1`, port wildcarded) — custom URI schemes are rejected for generic desktop clients. The Rust listener binds an ephemeral port per flow.
- Webview windows don't navigate custom-scheme anchors — route through `plugin-opener`.

### General

- **Load before you tear down.** `openFile` / `openNotebook` get the incoming file's bytes *first* and only then unmount what's on screen. An open can come back empty-handed — a provider that hasn't delivered the file, or an open the user superseded — and a teardown-first order turns every one of those into an app with nothing open, which reads as "my click closed the document". Supersession is also id-aware (`open-file-wait.js`): two opens racing for the *same* file are one intent, not a change of mind.
- Emit order matters around teardown: `clearActiveFile`/`openFile` emit unmount events *before* nulling the matching `current*` pointer, so listeners of those events read the *outgoing* surface; the fully-cleared state is only visible on the trailing `no-file-state` / `file-opened`. Two corollaries, both learned from the read-only Trash bar above the editor. **Test the pointers before the unmounts run, not after** — `deleteTreeNode` asked "was the open notebook the one deleted?" *below* the block that had just nulled `currentNotebookFileId`, so the answer was always no and a deleted notebook left the previous document's text in the editor instead of dropping to the empty pane. And **a listener that keys off "what is open" must be synchronous**: an `await` inside one lets a state read from the outgoing surface land after the pass that had already superseded it.
- **Finish letting go of a deleted surface before saving the tree.** `saveFileTree` emits `files-changed`, and by then the deleted node is already sitting in Trash — so anything asking "is the open file in the Trash?" got a yes about a file the user was in the middle of deleting. Clear the active file first; the save's own pulse then describes a state that is actually true.
- **`window.confirm` runs the delete before the user has confirmed it.** It doesn't reliably block in the WebView — it can return while the dialog is still on screen — so "Move to Trash?" moved the file to Trash behind the prompt still asking whether to. Use `showConfirmModal` / `showDeleteConfirmModal` (`sidebar/files-panel-shared.js`), or `gutter-commands.js`'s awaited variant.
- Keep per-keystroke and per-frame paths allocation-free and IPC-free: the naming-rule pipeline, notebook autosave gates (quiet-moment + backpressure), rAF-coalesced drag/scroll handlers, and dirty-driven render loops all exist because a single stall drops pointer samples (visible as straight-line gaps in ink).

## Companion deep links (`hushwriter://`)

Inbound channel for companion apps, routed by `src/links/deep-link-router.js` → per-feature handlers (`zotero-helper-import.js`). Current action: `hushwriter://zotero-import?desk=…&project=…&items=<json>&nonce=…` registers placeholder PDFs and background-downloads via Hush's own Zotero credentials (links never carry secrets); desk/project match by id then case-insensitive name; `project=__active__` targets the open project. Only a request with **no** `desk` parameter targets the active desk: a named desk that doesn't resolve is waited for (a local desk's folder routinely loads seconds after a cold launch) and, failing that, the import is refused with an error toast — the old silent active-desk fallback is how a cold-launch send (or a sender holding a renamed desk's old name) filed PDFs into the wrong desk. Registry writes happen before any tree access and the tree is then resolved and mutated in one synchronous pass, so a cross-window tree reload mid-import can't strand placeholders. New actions: parse in a sibling module, return `true` when recognized, remember the window boots hidden (`show()` before long work). Known gap: no `tauri-plugin-single-instance`, so Windows/Linux deep links may spawn a second instance.
